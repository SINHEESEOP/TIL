# 멱등성과 안전성

## 멱등성이란

멱등성(Idempotency)은 같은 연산을 한 번 실행하든 여러 번 반복 실행하든 결과, 즉 서버에 남는 상태가 동일하게 유지되는 성질이다.

수학적으로는 `f(f(x)) = f(x)`로 표현한다. 함수를 한 번 적용한 결과에 같은 함수를 다시 적용해도 값이 바뀌지 않는다는 뜻이다. 절댓값 함수 `abs(abs(x)) = abs(x)`가 대표적이고, `x = 5`라는 대입 연산도 몇 번을 실행하든 항상 x는 5이므로 멱등이다.

> [!NOTE]
> 멱등성은 원래 추상대수학에서 온 용어다. `a * a = a`를 만족하는 원소를 멱등원(idempotent element)이라 부른다. HTTP 스펙([RFC 7231](https://www.rfc-editor.org/rfc/rfc7231))은 요청을 재시도해도 되는지를 설명하기 위해 이 개념을 그대로 가져왔다.

### HTTP 메서드에서의 멱등성

| 메서드 | 멱등 여부 | 이유 |
|-------|:--------:|------|
| GET | 예 | 조회만 하므로 몇 번을 호출해도 서버 상태가 바뀌지 않는다 |
| PUT | 예 | "이 값으로 완전히 덮어써라"는 명령이라, 여러 번 보내도 최종 상태는 같다 |
| DELETE | 예 | 첫 호출 이후엔 이미 삭제된 상태다. 반복 호출해도 "삭제됨"이라는 상태 자체는 변하지 않는다 |
| HEAD, OPTIONS | 예 | 조회성 메서드라 상태 변경이 없다 |
| POST | 아니오 | "새 리소스를 생성하라"는 명령이라, 두 번 보내면 리소스가 두 개 생길 수 있다 |
| PATCH | 조건부 | 스펙상 멱등성이 보장되지 않는다. `필드 = 5`처럼 값을 지정하면 멱등이지만, `필드 += 1`처럼 증감 연산이면 비멱등이다 |

> [!IMPORTANT]
> 멱등성은 "응답이 항상 같다"는 뜻이 아니라 "서버에 남는 상태가 반복 호출로 더 바뀌지 않는다"는 뜻이다. DELETE를 두 번 호출하면 응답 코드는 200에서 404로 달라질 수 있지만, 리소스가 존재하지 않는다는 상태 자체는 첫 호출 이후 변하지 않으므로 여전히 멱등이다. 응답 코드가 같은지가 아니라 상태가 수렴하는지를 봐야 한다.

## 더 엄격한 상위 개념, 안전성

멱등성보다 한 단계 더 엄격한 조건이 안전성(Safety)이다.

| 구분 | 멱등성 | 안전성 |
|------|--------------------|--------------|
| 정의 | 반복 호출해도 상태가 더 이상 바뀌지 않는다 | 애초에 단 한 번의 호출로도 서버 상태를 바꾸지 않는다 |
| 허용 범위 | 상태를 변경하는 연산이어도 되지만, 결과가 한 지점으로 수렴해야 한다 | 조회 외의 동작을 허용하지 않는다 |
| 대표 메서드 | GET, PUT, DELETE, HEAD, OPTIONS | GET, HEAD, OPTIONS |

안전한 메서드는 전부 멱등하지만, 멱등한 메서드가 전부 안전한 것은 아니다.

```
전체 HTTP 메서드
 └ 멱등(Idempotent)
    └ 안전(Safe): GET, HEAD, OPTIONS
    + PUT, DELETE (상태를 바꾸지만 결과가 수렴)
 + POST, PATCH(일반적으로 비멱등)
```

PUT과 DELETE는 서버 상태를 실제로 바꾸는 연산이지만 반복해도 같은 결과로 수렴하기 때문에 멱등하되 안전하지는 않다. GET, HEAD, OPTIONS는 상태를 바꾸려는 시도 자체를 하지 않으므로 멱등성 조건을 가장 엄격한 방식으로 만족한다. 그래서 안전성을 멱등성보다 강한 조건이라고 부른다. 멱등성은 "반복해도 안전하다"는 정도를 요구하지만, 안전성은 "시도 자체가 상태를 건드리지 않는다"는 더 높은 기준을 요구한다.

## 실무에서 왜 이 구분이 필요한가

1. 재시도 전략 — 네트워크 타임아웃으로 응답을 못 받았을 때 PUT, DELETE, GET처럼 멱등한 요청은 재시도해도 되지만, POST는 함부로 재시도하면 리소스가 중복 생성될 수 있다.
2. 캐싱 — 안전한 메서드(GET, HEAD)만 브라우저나 프록시가 응답을 캐싱해도 무방하다. 멱등하다고 캐시 가능한 것은 아니다. PUT과 DELETE는 멱등하지만 캐시 대상이 아니다.
3. 크롤러와 프리페치 — 검색 엔진 봇이나 브라우저의 링크 프리페치는 안전한 메서드에만 적용해야 한다. GET 요청 하나로 회원 탈퇴가 처리되는 API를 만들면 크롤러가 실수로 회원을 탈퇴시킬 수 있다.
4. 결제 API의 멱등성 키 — Stripe나 토스페이먼츠 같은 결제 API는 원래 비멱등한 POST 요청에 클라이언트가 고유 키(`Idempotency-Key` 헤더)를 붙여서, 서버가 같은 키의 요청을 한 번만 처리하도록 강제한다. HTTP 메서드 자체가 아니라 애플리케이션 계층에서 멱등성을 흉내 내는 방식이다.

> [!TIP]
> 결제나 주문 생성처럼 중복 처리가 치명적인 POST API를 설계할 때는 멱등성 키 패턴을 먼저 검토하는 게 좋다. 클라이언트가 재시도해도 서버가 중복 요청을 걸러주기 때문에, 네트워크 오류 상황에서의 처리를 클라이언트 쪽에서 따로 구현하지 않아도 된다.
