# 🔁 멱등성(Idempotency)과 더 엄격한 상위 개념 — 안전성(Safety)

## 📝 멱등성이란?

**멱등성(Idempotency)**은 동일한 연산을 한 번 수행하든 여러 번 반복 수행하든 **결과(서버의 상태)가 동일하게 유지되는 성질**을 말합니다.

수학적으로는 `f(f(x)) = f(x)` 로 표현됩니다. 함수를 한 번 적용한 결과에 다시 함수를 적용해도 값이 변하지 않는다는 뜻입니다. (예: 절댓값 함수 `abs(abs(x)) = abs(x)`, 또는 `SET x = 5` 라는 연산 — 몇 번을 실행해도 x는 항상 5)

> 💡 이 용어는 원래 수학(추상대수학)에서 온 개념으로, `a * a = a` 를 만족하는 원소를 "멱등원(idempotent element)"이라 부릅니다. HTTP 스펙([RFC 7231](https://www.rfc-editor.org/rfc/rfc7231))은 이 개념을 요청 재시도의 안전성을 설명하기 위해 그대로 차용했습니다.

### HTTP 메서드에서의 멱등성

| 메서드 | 멱등 여부 | 이유 |
|-------|:--------:|------|
| GET | ✅ | 조회만 하므로 몇 번을 호출해도 서버 상태 불변 |
| PUT | ✅ | "완전히 이 값으로 덮어써라" → 여러 번 보내도 최종 상태는 동일 |
| DELETE | ✅ | 첫 호출 이후엔 이미 삭제된 상태 → 반복해도 "삭제됨"이라는 상태는 동일 (두 번째부턴 404가 나올 수 있지만, **자원의 상태**는 변하지 않음) |
| HEAD, OPTIONS | ✅ | 조회성 메서드이므로 상태 변경 없음 |
| POST | ❌ | "새 리소스를 생성하라"는 명령 → 두 번 보내면 리소스가 두 개 생성될 수 있음 |
| PATCH | ⚠️ | 스펙상 멱등성이 보장되지 않음. 구현에 따라 다름 (예: `필드 += 1` 방식이면 비멱등, `필드 = 5` 방식이면 멱등) |

**핵심 오해 주의**: 멱등성은 "**응답이 항상 같다**"는 뜻이 아니라 "**서버에 남는 상태(side effect)가 반복 호출로 인해 추가로 바뀌지 않는다**"는 뜻입니다. DELETE를 두 번 호출하면 응답 코드는 `200 → 404`로 달라질 수 있지만, 자원이 "존재하지 않는다"는 상태 자체는 첫 호출 이후 변하지 않으므로 멱등입니다.

## 🔒 더 엄격한 상위 개념: 안전성(Safety)

멱등성보다 **한 단계 더 엄격한 조건**이 바로 **안전성(Safe)**입니다.

| 구분 | 멱등성(Idempotent) | 안전성(Safe) |
|------|--------------------|--------------|
| 정의 | 반복 호출해도 상태가 **더 이상 바뀌지 않음** | 애초에 **단 한 번의 호출로도 서버 상태를 절대 바꾸지 않음** |
| 허용 범위 | 상태를 변경하는 연산이어도 됨 (단, 그 결과가 수렴해야 함) | 오직 조회(read-only)만 허용 |
| 대표 메서드 | GET, PUT, DELETE, HEAD, OPTIONS | GET, HEAD, OPTIONS |

즉 **모든 안전한(Safe) 메서드는 멱등하지만, 모든 멱등한 메서드가 안전한 것은 아닙니다.**

```
        ┌─────────────────────────────┐
        │   전체 HTTP 메서드            │
        │  ┌───────────────────────┐  │
        │  │   멱등(Idempotent)      │  │
        │  │  ┌─────────────────┐  │  │
        │  │  │  안전(Safe)      │  │  │
        │  │  │  GET, HEAD,     │  │  │
        │  │  │  OPTIONS        │  │  │
        │  │  └─────────────────┘  │  │
        │  │   + PUT, DELETE       │  │
        │  └───────────────────────┘  │
        │     + POST, PATCH(비멱등)     │
        └─────────────────────────────┘
```

- **PUT/DELETE**는 서버 상태를 실제로 바꾸는 연산이지만, 반복해도 결과가 같은 지점으로 수렴하기 때문에 멱등하되 안전하지는 않습니다.
- **GET/HEAD/OPTIONS**는 상태를 바꾸는 시도 자체를 하지 않으므로 멱등성의 요건을 자동으로, 그리고 가장 엄격하게 만족합니다.

이 때문에 "안전성"을 "멱등성의 더 강한 버전(stricter subset)"이라고 부릅니다. 멱등성이 요구하는 것은 "반복해도 안전하다"는 정도지만, 안전성은 "시도조차 상태를 건드리지 않는다"는 훨씬 높은 기준을 요구합니다.

## 🤔 왜 이 구분이 실무에서 중요한가

1. **재시도(Retry) 전략** — 네트워크 타임아웃 등으로 응답을 못 받았을 때, 멱등한 요청(PUT, DELETE, GET)은 재시도해도 안전하지만 POST는 함부로 재시도하면 중복 생성이 발생할 수 있습니다.
2. **캐싱** — 안전한 메서드(GET, HEAD)만 브라우저/프록시가 응답을 캐싱해도 무방합니다. 멱등하다고 해서 캐시 가능한 것은 아닙니다(PUT, DELETE는 멱등하지만 캐시 대상이 아님).
3. **크롤러/프리페칭** — 검색 엔진 봇이나 브라우저의 링크 프리페치(prefetch)는 안전한 메서드에만 적용해야 합니다. GET 요청 하나로 회원 탈퇴가 처리되는 API를 설계하면 크롤러가 실수로 회원을 탈퇴시킬 수 있습니다.
4. **분산 시스템/결제 API의 멱등성 키(Idempotency Key)** — Stripe, 토스페이먼츠 등 결제 API는 POST처럼 원래 비멱등한 요청에 클라이언트가 고유 키(`Idempotency-Key` 헤더)를 붙여 서버가 "같은 키의 요청은 한 번만 처리"하도록 강제로 멱등성을 부여합니다. 이는 HTTP 메서드가 아니라 애플리케이션 계층에서 멱등성을 흉내 내는 대표적인 패턴입니다.

## 🎯 정리

- **멱등성**: 여러 번 반복해도 결과(서버 상태)가 달라지지 않는 성질 — `f(f(x)) = f(x)`
- **안전성**: 멱등성보다 더 엄격한 개념으로, 단 한 번의 호출로도 상태를 절대 바꾸지 않는 성질 (Safe ⊆ Idempotent)
- 실무에서는 이 두 속성을 기준으로 **재시도 가능 여부, 캐싱 가능 여부, 크롤러 허용 여부**를 판단합니다.
- HTTP 메서드가 아닌 영역(결제, 메시지 큐, 분산 시스템)에서도 "멱등성 키" 같은 패턴으로 동일한 개념이 응용됩니다.
